avant d'ajouter quoi que ce soit d'autre.

## 🔄 LE PIPELINE

1. AVANT_TOUS  : charge le code source + langage.json, construit la table
                 de normalisation. Retourne (code_source, fichier_json).
                 Affiche "=== nom_fichier ===" au début.
2. LEXER       : Lexer(le_json, code_source, _commentaire).token
                 → lance la tokenisation via __post_init__.
                 Retourne list[Token] via .token.
                 Token = TypedDict {ligne, type, valeur}.
3. PARSEUR     : Parseur(token).ast
                 → lance l'analyse dans __init__.
                 Retourne Algorithme via .ast.
4. SEMANTIQUE  : AnalyseurSemantique(ast)
                 → lance l'analyse dans __post_init__.
                 Retourne rien (lève des erreurs ou passe).
5. INTERPRETEUR: Interpreteur(AST=ast)
                 → lance l'interprétation dans __init__.
                 Retourne rien (effets de bord).

main.py fait donc simplement :
    code_source, fichier_json = avant_lexer()
    token = Lexer(
        le_json=fichier_json,
        code_source=code_source,
        _commentaire=fichier_json["commentaire"]
    ).token
    ast = Parseur(token).ast
    ANA_SEMAN = AnalyseurSemantique(ast)
    interprete = Interpreteur(AST=ast)

## ✅ CE QUI MARCHE DÉJÀ (testé et validé)

Tests validés :
1. Hello World + x <-- 5 puis Ecrire(x) → 5
2. Bloc variable vide → erreur claire avec ligne
3. Tableau 2D M(2, 3) → 42
4. Fonction + retourne → 10
5. Commentaire bloc % ... % → OK
6. a <-- "a" (chaîne de 1) sur variable caractere → a (COMPATIBILITÉ HASSAN EL BAHI)
7. a <-- 'a' (caractère simple quote) → a
8. a <-- "az" (chaîne de 2) sur caractere → erreur claire
9. a <-- 'az' (2 caractères) → erreur LEXER claire
10. x <-- 5 avec x <-- (opérateur ASCII) → 5

Fonctionnalités validées :
- Syntaxe complète : algorithme, variables, constantes, tableaux 1D/2D,
  fonctions, procédures, si/alors/sinon, cas/vaut/sinon, pour, tant que,
  repeter/jusqu'a, ecrire, lire, retourne.
- Gestion des accents via sans_accents (unicodedata NFD).
- Insensibilité à la casse (sauf pour "a" traité contextuellement dans
  parse_pour).
- Commentaires en bloc : % ... %
- Gestion des portées (variables locales aux fonctions, globales).
- Tableaux 1D et 2D en paramètres et en retour de fonction.
- Copie profonde des tableaux à l'entrée des fonctions (pas d'effet de bord).
- Vérification sémantique : types, dimensions, initialisation, retour.
- Numéros de ligne dans TOUTES les erreurs (lexer, parser, sémantique,
  interpréteur).
- Messages d'erreur en français + anglais, colorés.
- Alias shell "evana" fonctionnel.
- Architecture POO du Lexer (classe Lexer hérite de AideLexer).
- Opérateur <-- (ASCII) reconnu, normalisé en ←.
- Synonymes de chaine : chaines de caractère, chaine de caractères,
  chaines des caractères, etc. Tous normalisés en chaine.
- Compatibilité Hassan El Bahi : "a" (chaîne de 1) affecté à un caractere
  est accepté, grâce à une règle d'affectation contextuelle dans le
  sémantique (pas dans le lexer).

## 🚨 CONTRAINTES ET RÈGLES DU PROJET

1. Le langage est INSENSIBLE à la casse (Algorithme, ALGORITHME, algorithme
   sont identiques). Sauf "a" qui est traité spécialement :
   - "a" minuscule dans "pour i ← 0 a 3 pas 1" = mot de liaison
   - "A" majuscule ou "a" hors contexte = identifiant valide
   Le lexer ne doit PAS traiter "a" comme mot-clé. C'est le parser
   (parse_pour) qui gère "a" contextuellement.

2. Unicité par portée : les variables peuvent avoir le même nom dans
   différentes fonctions. Seul le nom de l'algorithme est globalement unique.

3. Règles imposées par le créateur (SASORI) :
   - Un bloc "variable" doit contenir au moins une déclaration.
   - Un bloc "constante" doit contenir au moins une déclaration.
   - Un tableau 1D doit avoir des dimensions > 1 (suggérer une variable
     simple à la place).
   - Un tableau constant doit avoir au moins 2 éléments.
   - Pas de mélange tableaux 1D et 2D sur la même ligne de déclaration.
   - Pas de mélange tableaux et variables sur la même ligne.

4. Les commentaires sont UNIQUEMENT des blocs % ... %. Pas de
   commentaire de fin de ligne. Choix validé : fidélité au pseudo-code.
   Conséquence : un % dans un commentaire (comme "8%") termine le
   commentaire. C'est une limite documentée.

5. Tableaux limités à 2 dimensions maximum (en déclaration).
   Paramètres tableaux limités à 1D (nb_dimensions=1 par défaut dans
   le sémantique).

6. Pas de "goto", pas de "class", pas d'exceptions (sauf SignalRetour
   interne pour l'interprétation).

7. Opérateur d'affectation : ← en priorité, <-- en fallback ASCII.
   Les deux sont normalisés en ←.

8. Compatibilité Hassan El Bahi : le langage doit accepter 100% du
   pseudo-code du prof, même les notations non standard :
   - `a <-- "a"` : chaîne de 1 caractère affectée à un `caractere`.
     Accepté par une règle d'affectation contextuelle dans le sémantique.
   - Le lexer NE transforme PAS "a" (guillemets doubles) en CARACTERE.
     C'est une CHAINE. La conversion contextuelle se fait au moment de
     l'affectation.
   - `;` en fin de ligne : à ignorer (comme un espace). PAS ENCORE FAIT.
   - `8%` dans un commentaire : % termine le commentaire, c'est une
     limite documentée. L'utilisateur doit éviter % dans les commentaires.

## 🧪 PHILOSOPHIE DE DÉBOGAGE

- Quand un exo plante avec un beau message d'erreur EVANA (rouge + ligne) :
  c'est probablement une erreur de frappe dans le fichier .algo.
  Vérifier la ligne indiquée, corriger le .algo.

- Quand un exo plante avec un Traceback Python (peur, pas rouge) :
  c'est un trou dans la raquette du compilateur.
  Envoyer le code .algo + le message d'erreur à l'IA.

- Quand un exo produit un résultat faux sans erreur :
  c'est un bug sémantique ou d'interprétation.
  Isoler le cas minimal, vérifier avec afficher_ast.py.

- Règle d'or : ne PAS corriger un bug avant d'avoir vu les 70 exos.
  Noter les bugs, mais prioriser après avoir la liste complète.

## 💡 PERFORMANCE (contexte)

Sur Hello World :
- EVANA : ~0.10s (Python + AST direct)
- Dart  : ~0.32s (VM + JIT)

EVANA est plus rapide au démarrage, mais sera beaucoup plus lent sur du
calcul pur (1000x à 2000x plus lent sur une boucle de 1M d'itérations).
Ce trade-off est acceptable pour un usage pédagogique.
